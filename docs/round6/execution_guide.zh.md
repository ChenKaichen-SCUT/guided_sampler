# Guided Sampler 第六轮：CCSS 停滞守卫、混合搜索预算回收与覆盖收益验证

## 0. 总任务与执行要求

在 GitHub 仓库 `ChenKaichen-SCUT/guided_sampler` 中，从冻结提交 `ae85956068154207a442c0e2c8387c573dc32411` 建立独立分支 `round6-guarded-coverage-validation`。

本轮必须完成以下工作：

1. **实现并独立检验CCSS长期无全局改善时的提前交还守卫。**
2. 在完整HighDiv混合采样流程中，检验守卫是否真正释放时间、使后续查询获得执行机会，并最终增加合法不同模型和AST-bit覆盖。
3. 比较相同守卫下的无覆盖软参考与覆盖指导，区分通用成本控制收益和覆盖信息的额外收益。
4. 根据前两轮证据及本轮守卫验证结果，按预先登记的规则选取至多一个进一步的算法改进，实现独立消融。
5. 只有满足晋级条件，才执行八实例、900秒与100模型预算的正式验证，并与冻结完整HighDiv比较。

最终目标仍然是：**同时改善相同墙钟时间和相同正式模型数下的官方AST-bit覆盖。**

不能仅凭CCSS更快返回Unknown、增加查询次数或提高自选目标命中数量宣称成功。

原始HighDiv目录、8个SMT输入、历史实验与已归档正式结果保持不变。全部使用seed=0；禁止重跑冻结HighDiv基线、追加seed、启用B、改变LIA move或为提高成绩临时调参。

## 1. 冻结的研究证据与假设

先核对以下来源：

- [第五轮完整报告](https://github.com/ChenKaichen-SCUT/guided_sampler/blob/ae85956068154207a442c0e2c8387c573dc32411/docs/round5_weak_targets_and_ccss_results.zh.md)
- [第五轮下一步决策](https://github.com/ChenKaichen-SCUT/guided_sampler/blob/ae85956068154207a442c0e2c8387c573dc32411/results/round5/analysis/next_change_decision.json)
- `src/round5/ccss_probe.inc`
- `src/round5/ccss_replay_main.cpp`
- `src/round5/soft_phase.inc`
- `include/round5/coverage_policy.hpp`
- 上游 `z3/src/sampler/sampler.cpp`

现有证据：

**H1：CCSS模型交换状态影响搜索难度。** 在冻结convert捕获中，M_ref于219步完成；M_full和空map均持续至52秒截止。两种map改变了初始化区间和初值，但初始未满足集合相同。该捕获支持map导致搜索退化，不证明所有实例如此。

**H2：局部目标收益可能被后续供给损失抵消。** 第五轮convert共同前三个模型中，Full相对Ref增加492个covered bit，但60秒完整会话少8789个bit。

**H3：提高已选目标命中不一定提高全部覆盖。** random、real的同样本质量退步主要发生在G2，即原本已有单侧观察但不在共同初始映射池中的位。

**H4：删除avoid不是已经成功的改进。** 第五轮没有发现avoid独占额度而阻塞仍可执行support的案例；support-only整体表现没有优于Full。

本轮优先验证H1能否转化为真实的时间与覆盖收益，同时检验H2、H3是否仍限制最终性能。

## 2. 阶段G0：实现单因素CCSS停滞守卫

### 2.1 只能修改哪些行为

主要修改：

- `z3/src/sampler/sampler.cpp::ls_sampler::search()`
- `ls_sampler::update_best_solution()`附近的全局best更新记录
- `z3/src/sampler/sampler.h`中的必要守卫状态
- CCSS返回原因传递及轻量计数日志
- 第五轮独立replay入口

不允许修改原生搜索的：

- 变量与move选择；
- 初始化分布、区间及模型交换map；
- 随机数产生和消费顺序；
- 原有重启条件；
- CDCL/CCSS交替结构；
- 原有CCSS cutoff；
- 模型恢复和正式样本接纳规则。

新增的唯一生产机制，是允许CCSS在连续长期无全局改善后，提前返回宿主。

### 2.2 守卫语义

固定阈值：

`STAGNATION_LIMIT = 65536` 个原生搜索步。

本次CCSS调用中的全局best，指 `_best_found_cost` 所代表的最少未满足子句数。

**只有严格降低该全局best才算改善。**

每次调用重新初始化守卫状态；但原生CCSS内部重新初始化、重启、模式切换，不得重置守卫的全局改善历史。

不得直接把现有 `no_improve_cnt` 当成全局停滞计数，因为原代码存在restart局部改善和全局改善的区别。

建议增加明确状态：

```cpp
struct StagnationGuard {
    bool enabled = false;
    uint64_t last_global_improvement_step = 0;
    uint64_t final_step = 0;
    int best_global_cost = INT_MAX;
    bool yielded = false;
};
```

算法流程：

```text
开始CCSS调用：
    初始化原生搜索与守卫；
    记录第一次有效全局best。

每次原生移动、更新或重新初始化后：
    如果实际全局best严格下降：
        更新best；
        记录last_global_improvement_step。

每步检查：
    如果原生已经找到零未满足的合法解：
        优先执行原有成功路径。
    否则如果步数减去最后严格改善步数 >= 65536：
        正常交还宿主。
    否则继续原生搜索。
```

必须捕获所有能够真正降低 `_best_found_cost` 的位置，包括 `initialize()` 内部的更新。不能只观察移动循环末尾。

需要特别保证：如果某次移动刚把未满足数降为0，不允许同一步的守卫抢先丢弃这次成功；仍走原生恢复与验证。

### 2.3 正常交还的语义

守卫触发时：

```text
reason = ccss_stagnation_yield
result = Unknown
formal_model = none
```

不返回UNSAT，不返回近似解，不调用成功模型恢复，不更新 `m_ls`，也不假装该次CCSS产生了样本。

宿主继续原有HighDiv主循环，使之后的CDCL或CCSS有机会执行。

保留原生time cutoff与外层会话截止。必须分别记录：

- `ccss_stagnation_yield`
- `native_cutoff`
- `host_deadline`
- `arith_unknown`
- `exception`

不能把它们都归入普通Unknown。

### 2.4 日志字段

每次CCSS调用至少记录：

```text
call_id
source_query_id
guard_enabled
stagnation_limit
map_sha256
initial_global_best
last_global_best
last_improvement_step
exit_step_exact
max_stagnation_steps
restart_count
initialization_count
exit_reason
search_cpu_seconds
search_wall_seconds
whole_ccss_wall_seconds
rng_before / rng_after hashes
model_produced
```

日志必须记录精确退出步数，修复第五轮只能从最后进度点得到下界的问题。

热路径只增加常数级整数更新与有界检查，不进行字符串序列化、AST打印、模型求值或I/O。

### 2.5 正确性验证

完成Release、ASan/UBSan及以下受控测试：

- 守卫关闭：原生轨迹、RNG、初始化、模型与冻结版本一致。
- 219步成功例：开启守卫后仍然正常成功。
- 长停滞例：明确返回 `ccss_stagnation_yield`。
- 内部restart不会重置全局停滞历史。
- restart中出现严格更好的全局best，会正确刷新历史。
- 已达到零未满足时不会错误交还。
- cutoff、取消、溢出、异常与守卫同时接近触发时，返回原因可区分。
- CCSS返回Unknown后宿主和下一次查询可以继续。
- 禁用守卫时，不得增加随机数消费或隐藏的模型调用。

不得扩大既有上游泄漏抑制范围。

## 3. 阶段G1：先用冻结CCSS捕获独立验证

使用第五轮已经归档的构造配方、完整map及R0状态，执行六项守卫开启的独立重放：

| 重放 | 配方 | map | 预期检验 |
|---|---|---|---|
| G_rr | H_ref | M_ref | 219步快解不被截断 |
| G_cr | H_full | M_ref | 相同快解不被截断 |
| G_rc | H_ref | M_full | 长停滞应提前交还 |
| G_cc | H_full | M_full | 长停滞应提前交还 |
| G_r0 | H_ref | 空map | 记录另一类失败的交还 |
| G_c0 | H_full | 空map | 验证配方独立性 |

原生重放上限保留52秒，父进程保护与第五轮一致。只执行一次，不因某格结果不理想而重跑。

逐项核对：

- R0—R3状态与原生捕获在相应边界一致；
- 守卫触发之前的移动结果与已保存原生进度证据一致；
- 快解仍然成功；
- 长失败交还时best非零，且没有把Unknown写成SAT；
- CPU、墙钟、最后改善步数与实际退出步数均已记录。

这一阶段只能证明守卫对约简CCSS搜索的效果，**不能产生新的正式模型或官方覆盖成绩**。

如果快解被错误截断、构造不一致、产生非法候选或RNG意外变化，停止后续性能实验并报告失败。

## 4. 阶段G2：完整HighDiv中检验“节省的时间是否有用”

使用同一个新Release构建，仅切换策略与守卫开关。

| 配置 | 历史参考 | 覆盖指导 | CCSS停滞守卫 |
|---|---|---|---|
| `Ref` | 软参考 | 无 | 关闭 |
| `RefG` | 软参考 | 无 | 开启 |
| `Full` | 软参考 | 第五轮Full | 关闭 |
| `FullG` | 软参考 | 第五轮Full | 开启 |

保留原生选变量、4次覆盖建议、64决策窗口、reference回退、map交换和CCSS。

这四组能够区分：

- `FullG−Full`：守卫对当前覆盖策略的影响。
- `RefG−Ref`：守卫对无覆盖软参考策略的影响。
- `FullG−RefG`：相同成本保护下，覆盖信息的额外价值。

不能只比较 `FullG` 与 `Full` 就宣称覆盖指导有效。

### 4.1 开发实例与预算

实例固定为：

`convert`、`SMT_random`、`SMT_real`。

每个配置运行两个**独立会话**：

- `time120`：120秒，无模型数量限制，也不设置人为CDCL查询数量限制。
- `n20_t120`：达到20个正式、不同、合法模型时停止，否则最多120秒。

总计：3实例 × 4配置 × 2模式 = **24次会话**。

全部seed=0。不得用 `time120` 的前20个模型冒充独立 `n20_t120`。

如任何运行未达到20模型，应保留实际数量及超时状态；只能比较双方真正共有的前缀，不能宣称严格20模型胜负。

### 4.2 并行与资源公平

使用固定的CPU绑定和同步起跑。每个实例的四配置放在四个不同物理核上构成一批，预先登记配置到CPU的轮换；不在实验中途动态增补其他任务。

不同实例、不同预算模式按冻结顺序运行。构建、审计、压缩及上传不与计时会话并行。

记录进程wall、user+system CPU、RSS、CPU亲和性及实际退出延迟。正式模型的接纳时间严格受原预算截止约束。

### 4.3 必须记录“节省的时间去了哪里”

只记录CCSS提前返回是不够的。

为每个 `ccss_stagnation_yield` 建立独立事件：

```text
本次CCSS开始
→ 最后全局best改善
→ 触发守卫
→ 正常交还宿主
→ 下一次CDCL开始
→ 下一次合法模型产生
→ 下一次新增covered出现
```

统计：

1. 交还调用数、累计交还前耗时；
2. 本轮新增加的后续CDCL检查数；
3. 新增加的CCSS调用数；
4. 新交付的合法不同模型数；
5. 重复模型数；
6. 这些后续模型实际新增的covered bit；
7. 下一次成功模型与下一次正覆盖所需时间；
8. 直到会话截止，累计还有多少次交还但没有带来正式模型。

必须区分**局部重放中的可节约时间**与**实际端到端新增产出**。搜索轨迹分叉后，不能用两次完整运行的耗时差当作精确因果节约。

### 4.4 同时评价模型数量与质量

按冻结官方 `calc_metric.py` 和同口径精确bit计数，报告：

- 120秒终点covered/total；
- 每个正式模型的新增covered；
- covered随时间变化和AUC；
- 首10/20个模型覆盖；
- 达到20模型的秒数；
- 正式模型数、重复率、CDCL/CCSS来源；
- G1/G2/G3覆盖差值；
- 指定目标命中及全式净覆盖；
- 每个CCSS调用的退出原因、CPU和墙钟。

同样样本数时，必须比较精确集合覆盖，而不是只比较模型数或指定目标成功次数。

### 4.5 守卫的验收结果分级

**G-PASS-LOCAL：** 独立重放证明守卫安全截断长停滞，快解不受影响。

**G-PASS-TIME：** 完整会话中出现实际交还，且显著减少长失败调用占用的时间。

**G-PASS-USEFUL：** 在相同时间内，实际增加后续查询机会、合法不同模型及官方全式covered，而不是只增加Unknown次数。

**G-PASS-COVERAGE：** `FullG`相对`RefG`在相同时间、相同正式模型数下仍有覆盖优势。

四级必须分别报告。达到前两级，不可自动宣称达到后两级。

## 5. 阶段G3：根据实测结果确定本轮唯一算法候选

G2全部完成并独立审计后，**先冻结结论，后修改算法**。

以下选择规则必须在G2运行前写入manifest。不得实验后新增第三种算法或临时搜索阈值。

| G2的实际结论 | 下一步 |
|---|---|
| 守卫损害正确性或截断快解 | 停止，No-Go |
| 守卫没有有效节省时间 | 停止，分析失败原因 |
| 守卫节省时间，但后续没有新增合法模型；且反复遇到同一实际消费map的停滞 | 可选择一次“同map停滞冷却”候选 |
| 守卫增加模型供给，但FullG仍因G2/G3损失而低于RefG | 选择“覆盖/参考交替调度”候选 |
| FullG已经在等时间和等样本方面优于RefG | 不添加新机制，直接以FullG晋级验证 |
| 证据不足以支持上述任一改进 | No-Go，保留全部负证据 |

**只允许选择其中一个候选。**

### 候选A：Guarded Alternating Coverage Sampling

该候选针对第五轮观察到的模型质量损失。

核心思想：

> 保留覆盖指导能够实现特定观察的能力，但不让每一次CDCL查询都被覆盖偏好改变；在覆盖引导与软参考搜索之间交替，兼顾局部缺口和其他未映射观察。

新增一个查询级确定性选择：

```text
首次CDCL调用：
    无历史缺口时按原生逻辑运行。

后续CDCL调用：
    第1次使用Full；
    第2次使用Ref；
    第3次使用Full；
    第4次使用Ref；
    依此交替。
```

首次有可用覆盖历史后的奇偶规则必须在实现前固定，不能因为convert某个历史成功查询的编号而调换起始相位。

Full轮次仍使用原来的support/block评分及4次额度；Ref轮次只使用历史软参考与原生相位。**两种轮次都开启同一个CCSS停滞守卫。**

不改变：

- 单个原生决策的选择；
- 覆盖目标定义；
- 语义映射；
- reference来源和RNG；
- CCSS模型交换；
- 原生relevance；
- 样本接纳与官方指标。

建议新增：

```text
CoverageSchedule = AlwaysFull | Alternating | ReferenceOnly
```

在外层CDCL查询边界设置本次schedule，不在求解过程中反复切换。

这是固定的1:1交替候选，不增加25%、75%等参数搜索。

### 候选B：Repeated-Stagnation Cooldown

只有G2实际记录了**相同消费map反复导致停滞且没有新增正式模型**，才允许实现。

保持Guard开启。若连续两次CCSS均因停滞交还，且实际消费的map内容哈希相同、中间未出现新的合法CDCL模型，则跳过下一次原定的CCSS调用一次，让宿主继续CDCL。

跳过一次后恢复正常尝试，不能永久禁用CCSS。

此方案只针对“释放时间后再次落入同一无效搜索状态”，不对任何首次Unknown直接冷却。

必须记录跳过原因、map身份和对应RNG处理规则，并承认这种调度改变会影响后续随机流和模型历史。

如果G2没有上述重复状态证据，不实施候选B。

## 6. 阶段A：对唯一选定算法进行消融

如果阶段G3选择候选A，比较：

| 配置 | CCSS守卫 | 覆盖查询策略 |
|---|---|---|
| RefG | 开启 | ReferenceOnly |
| FullG | 开启 | AlwaysFull |
| AltG | 开启 | Alternating |

如果选择候选B，则对照改为RefG、FullG和FullG+Cooldown，其他测试与评价规则不变。

只在三个开发实例执行，与G2相同的：

- `time120`
- `n20_t120`

每个候选及两个对照都使用同一候选阶段Release构建，重新完成匹配对照，不能因G2旧二进制或不同资源批次的结果有利而直接拼表。

最大实验量：3实例 × 3配置 × 2模式 = **18次短会话**。

候选改进必须单独比较：

- 与FullG相比是否改善；
- 与RefG相比是否仍有额外收益；
- 同样模型数下是否保住更多G2/G3覆盖；
- CCSS守卫是否继续发挥作用；
- 有没有增加重复模型、Unknown或者长时间停留；
- 实际新增模型是否真的带来新增covered。

### 晋级条件

只有满足以下条件才考虑900秒正式实验：

1. 当前候选在开发实例的等时间平均精确覆盖变化为正。
2. 在能完成严格20模型的实例上，等样本平均覆盖变化也为正；未完成的实例不得算作平局或胜利。
3. 需要至少两个开发实例出现严格正收益，不能全靠convert一例。
4. 不出现新的非法模型、求解状态损坏、RNG异常或无法解释的持续性能灾难。
5. 守卫至少在一个真实实例中带来有用的后续合法模型和新增covered，而不只是更早返回Unknown。

上述比较以同样开启守卫的RefG为核心对照，同时保留FullG消融。

如果没有任何候选达到条件，停止，不执行900秒矩阵。报告应明确说明守卫是否有效、为什么没有转化为覆盖收益，以及下一项真正需要研究的是模型质量还是搜索供给。

## 7. 阶段F：八实例正式性能确认

只允许在阶段A晋级之后执行。

## 8. 特别需要防止的错误结论

**错误一：守卫越早返回Unknown越好。**

正确评价是它是否让剩余时间产生更多有用模型。若不断快速Unknown，却没有正式模型和新增覆盖，应判为时间回收未转化为收益。

**错误二：FullG比Full好，就证明覆盖反馈有效。**

仍需比较RefG。通用停滞保护可能同样帮助无覆盖版本。

**错误三：指定的G1目标增加，就说明算法提高整体覆盖。**

必须检查G2/G3。第五轮已经有G1改善而全式下降的例子。

**错误四：固定map在约简CCSS中成功，就算正式采样成功。**

重放验证范围仍然是约简CCSS；只有完整宿主恢复原始模型、验证原公式并完成正式接纳后，才允许进入覆盖统计。

**错误五：同样seed和相同前缀就意味着完整内部状态相同。**

必须区分共享外层输入、RNG、原生构造状态与完整学习状态。不同会话只作对照，不冒充同状态因果实验。

**错误六：为了取得900秒正结果，调整守卫阈值、交替比例或增补seed。**

阈值65536、交替1:1和实验选择规则都必须事先冻结。负结果应直接报告。

## 11. 最终研究目的

本轮要完成的不是简单的代码优化，而是验证一条完整机制假设：

**覆盖指导可能提高部分模型的目标观察能力，但它也可能产生难处理的CDCL交换状态，使CCSS长时间不返回，减少后续模型供给；另一方面，过度偏向当前可映射目标，还可能损失其他AST-bit的探索。**

因此，新算法试图同时建立：

```text
覆盖需求参与软相位选择
        ↓
有机会得到更有价值的模型
        ↓
如果CCSS长期无改善，及时交还时间
        ↓
继续生成其他合法、不同模型
        ↓
必要时交替覆盖指导与普通参考搜索
        ↓
提高完整会话的AST-bit总覆盖
```

必须用独立实验逐段检验这条路径。

**成功标准不是守卫触发次数，也不是单个目标命中次数，而是在完整HighDiv混合框架中，将这些机制转化为相同时间和相同模型数下的真实覆盖提升。**

如果没有做到，也必须准确指出究竟是时间没有释放、释放后没有有效模型、模型质量下降，还是覆盖收益仍被其他位置抵消，并以此作为下一项算法研究的依据。
